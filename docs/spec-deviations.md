# Deviations from the architecture specification

Each entry names the spec section, what the code does instead, and why. None changes a gate or a verdict rule.

| # | Spec | Implementation | Why |
|---|---|---|---|
| D1 | §5 `ScientificProtocol` has five methods | Adds `task_kinds() -> TaskKindRegistry` | The kernel validates a `ComputePlan` against the registry (KRN-012) before execution; a module must declare its task kinds and their CPU reference implementations somewhere the kernel can see without importing the module. |
| D2 | §5 `validate(findings, predeclaration)` | `validate(findings, predeclaration, *, experiment_id)` | The `ValidationReport` schema requires `experiment_id`; passing it keeps reports self-describing without the module reaching into kernel state. |
| D3 | §5 driven ports list | Adds `HypothesisRepository`, `PredeclarationRepository`, `ExperimentRepository`, `DossierRepository`, grouped in a `UnitOfWork` | KRN-010 needs state changes and their events in one transaction; a unit of work over typed repositories is the smallest port that expresses that. |
| D4 | §5 domain events (13) | Adds `ExperimentRefused` | The lifecycle diagram has a Refused state and KRN-003 requires the refusal to be recorded; an event is how every other state change is recorded. |
| D5 | §7 `SourceRef` requires a DOI for documents | Accepts a DOI or, for works that have none, an ADS bibcode | Several 1919–1920 eclipse papers have no DOI. The schema's `if/then` rule mirrors this. |
| D6 | §9 kernel trusts `validate()` | The kernel re-evaluates the frozen gates and refuses a report whose checks differ (`VerdictInconsistent`) | Defence in depth for KRN-009; it is the in-process form of the harness re-derivation (TST-007). |
| D7 | §10 checkpoint format unspecified | Canonical-JSON codec with tagged `.npy` arrays (no pickle), Arrow IPC tables, and tagged integral or non-finite floats | Identical results give identical artifact ids; a resumed task receives exactly the types it wrote. |
| D8 | §10 curated datasets | Curated Parquet files carry `sdp.dialect` and `sdp.raw_parent` schema metadata | DSI-005 is then visible in the file itself, and a curation that renames nothing still gets its own content address. |
| D9 | Investigate §4 `ObservationArchiveGateway.fetch` and `cutout` return a `DatasetArtifact` | They return a `FetchedProduct` (bytes, media type, release, licence, citation and the URI actually read); `InvestigateField` checksums and registers the `DatasetArtifact` | Registration and its `DatasetAcquired` event then commit in the kernel's unit of work, and the checksum is computed by the kernel from the bytes as read (INV-005, INV-013), the same split `ArchiveGateway.fetch` already uses. |
| D10 | Investigate §2 "a frozen predeclaration naming evidence the investigation did not use" | The predeclaration names that evidence in `parameters.confirmatory_evidence` as `{kind: archive \| release \| epoch \| region, value}` items; promotion needs at least one item the investigation's recorded `evidence_used` does not cover | The predeclaration schema has no evidence field; `parameters` is hashed with the rest, so the named evidence is frozen with it. |
| D11 | Investigate §2 Promoted investigations are read-only | Promoted allows exactly one further transition, to Closed with a reason | The state table also lists "failed confirmation" as a reason to close; nothing else (notes, parking, re-opening) is allowed after promotion. |
| D12 | §8 `quality_flags` is a JSON object column | Curated Parquet stores it as a canonical-JSON string | Parquet has no schemaless object type; a canonical string keeps the native flags verbatim and byte-stable, and DuckDB's `json` functions read it. |
| D13 | §8 lists HR23 and CGA20 as registered sources | Packaged TAP sources in this release are Gaia DR3, 2MASS PSC and PS1 DR2; the two benchmark catalogues arrive with the stellar module | They are cluster and membership tables, not astrometry rows; their dialects belong with the benchmark cross-match that uses them. |
| D14 | §10 `BenchmarkCrossMatch` goes through `CrossMatchService` | The benchmark cross-match is computed inside `sdp_stellar.benchmark` with astropy, against benchmark tables supplied as experiment inputs | It compares a handful of cluster centres within a radius *and* a proper-motion window; the positional `CrossMatchService` port does not express the window, and the benchmark tables are versioned inputs whose release, licence and citation the run checks (STL-G-02). |
| D15 | §10 candidate checks (stability, CMD coherence, membership) | Their thresholds are module constants in `sdp_stellar.analysis` (stability ≥ 0.5, at least 10 members at membership ≥ 0.5, CMD sequence at least 3× tighter than the field) rather than predeclared parameters | The draft predeclaration has no field for them. They should move into `parameters` before the UC-01 predeclaration is frozen, so changing them changes the hash. |
| D20 | Investigate §7 binds astroquery (SIMBAD) and pyvo (registry) | `SimbadResolver` asks SIMBAD's TAP service and the CDS Sesame resolver directly, and `RegTapRegistry` sends RegTAP the query pyvo's `regsearch` sends, both through the archive `Transport` | Every remote call then records and replays as a cassette (ADR-015), so CI never calls a live service; astroquery and pyvo own their HTTP sessions and cannot be replayed. The ADQL mirrors theirs, and INV-011 still forbids either package outside `sdp.adapters`. |
| D21 | Investigate §3 resolver records carry a source release | SIMBAD's release label is `simbad:live` | SIMBAD is a living database with no releases; the cassette records the date each answer was read. |
| D22 | Investigate §4 records a product's cloud URI where MAST serves one (INV-013) | `MastObservationGateway` leaves `cloud_uri` None and reads the ObsCore `access_url` | ObsCore lists no cloud copy, and MAST's cloud listing is a separate astroquery call that cannot be replayed from cassettes (D20). The checksum is still of the bytes actually read, and INV-013 holds trivially until a cloud lookup over the Transport is added. |
| D23 | Investigate §4 `cutout` returns the cutout as read | HAPCut answers with a zip and DASCH with base64 gzip inside JSON; the gateways return the FITS file inside, and DASCH DR7 cutouts have a fixed size, so `size` is not sent to DASCH | The zip and the encoding are transport containers, not the product; detectors read FITS. The checksum is of the FITS bytes the kernel registers. |
| D24 | Investigate §4 products reach tests as registered artifacts | A `ProductDialect` port curates a raw product into the canonical `lightcurve` or `astrometry` CSV (`sdp.kernel.science.products`); Retrieve registers the raw product, then the curated child through `DatasetArtifact.curate` with the dialect named, and `ProductEvidence.raw_artifact_id` points back to the raw one | The same raw/curated split as catalogue rows (DSI-005), so a test reads one canonical format whatever the archive. A dialect that changes nothing leaves the raw product to be read. |
| D25 | Investigate §6 long-baseline motion uses plate position errors | `DaschDialect` uses DR7 `drad_rms2` (arcsec) as the position error and a declared `default_pos_err_mas` (1000 mas) where DASCH gives none (its 99 flag) | DR7 publishes no per-point astrometric error. The default is an open question for review, and it is recorded with the dialect version. |
| D26 | Investigate §6 ranking reuses the stellar `CandidateRanker`, including novelty from the resolver and benchmark cross-match | Under the `stellar` policy, `StellarCandidateRanker` scores a co-moving group from its structure test's membership, CMD coherence and stability across the profile's `clusterer_grid`. Novelty is left out, as are CMD coherence and stability when the test could not assess them; the score is the weighted mean of the terms assessed, in [0, 1] like a single object's significance score. A group whose structure test is not significant at the policy's alpha scores 0 | Investigate does not cross-match structures against a benchmark cluster catalogue yet, and a SIMBAD match on a member star does not say whether the group is known. Leaving it out, rather than scoring it 0, keeps group and object scores on one scale under one threshold. |
| D30 | Integration v0.4.0 §4 `Detection` | The association record is `sdp.kernel.domain.association.Detection` (position covariance, epoch, resolution, product and extension); the Investigate `sdp.kernel.ports.investigate.Detection` (a detector's pixel and sky position) is unchanged | Two different things share the doc's word; the association record carries what a probability needs, the detector output carries what a detector produces, and the Identify stage converts one into the other. |
| D31 | Integration v0.4.0 §2, §7 `pyvo` and `astroquery.mast` for discovery and product inventory | RegTAP, VOSI, ObsTAP and the MAST product listing are spoken over the archive `Transport`, not through `pyvo`'s or `astroquery`'s own sessions (as Investigate D20) | CI replays every archive exchange from cassettes (ADR-015); libraries that own their HTTP session cannot be replayed. |
| D32 | Integration v0.4.0 §9 "the manifest gains `plan_artifact_id` and `adapter_compatibility[]`" | `plan_artifact_id` sits in the manifest's `intent`, `adapter_compatibility` in its `environment` group | The plan is part of what the run set out to do; the compatibility records describe the code that ran, beside the CPU/GPU agreement record as §6 says. |
| D33 | Integration v0.4.0 §9 `ProductNormalizer` as its own dialect | `ProductNormalizer` extends the Investigate `ProductDialect` port: `curate` stays the dialect's, `normalize` fills the envelope | One dialect per mission and release, not two parallel ones (agreed with the Investigate train). |
| D34 | Integration v0.4.0 §7 JWST products read through `stdatamodels` / `jwst` datamodels | `JwstDialect` reads headers and extensions with `astropy.io.fits` (`memmap=False`) inside `sdp.adapters.products` | The envelope needs keywords, extension names and the WCS, which plain FITS gives; `stdatamodels` pulls in ASDF and the pipeline's schemas for no extra field. It stays a bound package and can replace the reader behind the same dialect. |
| D35 | Integration v0.4.0 §3 "JWST reference products verified by two people" | Reference records start at `to_verify`; only `verified` records with two distinct verifiers admit an adapter, and the synthetic products are marked `synthetic` and never admit one | The sandbox cannot reach MAST, so the real reference products come from a recording run; until then T5s runs on synthetic JWST-layout files. |
| D36 | Integration v0.4.0 §6 "a manifest that names an adapter" | Each manifest input names its `adapter` and `product_type` (manifest 1.3.0), copied from the dataset artifact's `product` (dataset-artifact 1.1.0); the harness `claims` check compares descriptors with the compatibility records, not with the descriptor's own `conformance` map | The v0.4.0 manifest fields say which records exist, not which adapter and product type each input used, so admission could not be checked from the manifest alone; a descriptor's own map is the claim being checked, so it cannot be the evidence for it. |
| D37 | Integration v0.4.0 §2 `PyvoRegistryAdapter`, hand-written descriptors as YAML, cutouts discovered per product | `VoCapabilityDiscovery` speaks RegTAP, VOSI and ObsTAP over the `Transport` (D31); hand-written descriptors are JSON in the descriptor schema under `capabilities/descriptors/`; the descriptor records `per-product` when a service declares DataLink and `soda` when it declares SODA, and the per-product answer is read from each product's DataLink rows at ingestion (Stage A); Investigate's `SourceRegistry` is answered from registered descriptors instead of the open IVOA registry | Recordings replay in CI; one schema and one validator for both origins; a service-level flag says where to look, the product's own links say what is there; a stage should only find sources SDP has described. |
